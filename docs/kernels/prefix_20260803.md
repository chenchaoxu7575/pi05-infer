## Why this table has different columns from the denoise one

The denoise page answers *what is left to optimize* and is keyed on `FLOP/byte` and roofline
side, because every one of its kernels is memory-bound and sits 3x left of the knee. The
prefix is the opposite regime: both phases are compute-bound, 4.8-5.9x **right** of the knee,
so the question is *which of these GEMMs is near peak and which is not*. The columns are
therefore **achieved TFLOP/s** and **% of achievable bf16 peak**.

**There is deliberately no `FLOP/byte` column.** Neither prefix phase has an ncu-measured
DRAM byte count anywhere in the record; the intensities that exist are computed from
compulsory weight traffic, which is a *lower bound on bytes* and therefore an *upper bound*
on intensity. Publishing an upper bound in a column a reader will take for a measurement is
the error this page is written to avoid. Closing it needs
`ncu --metrics dram__bytes_read.sum` over the two prefix phases; that has never been run.

Peak is **206.2 TFLOP/s**, the bf16 rate at the 1897 MHz these kernels ran at
(`110 SM x 1.897 GHz x 1024 FLOP/SM/clk x 0.965` measured tensor-pipe efficiency). The
194.9 TFLOP/s constant elsewhere in the record is the same card at 1792 MHz; dividing these
times by it would overstate every number here by 5.9 %.

### The 25.5 points that are not FLOPs are mostly not the residue

At 74.5 % MFU, 25.5 points of the phase are not doing useful FLOPs. Splitting that:

```
ideal time, all 3756.15 GFLOP at 206.2 TFLOP/s   = 18 216.1 us
actual phase                                     = 24 443.2 us
                                              overhead 6 227.1 us
   of which  non-GEMM residue                       1 533.2 us   (24.6 %)
             GEMMs running below peak               4 694.0 us   (75.4 %)
```

Equivalently `74.5 % = 79.5 % GEMM attainment x 93.7 % GEMM share of phase time`.

**So three quarters of the gap is inside the GEMMs, not beside them.** Deleting the entire
non-GEMM residue -- every norm, every rotary apply, the softmax, the GeGLU activation, all of
it, to zero -- would move the phase from 24 443 us to 22 910 us and the MFU from 74.5 % to
79.5 %. The residue is real and it is now visible, but it is 6.3 % of the phase, and any
larger prefix win has to come from the GEMM rows.

Within those rows the money is unambiguous: the three MLP GEMMs are **79.5 % of the phase
time** and already run at 80-84 % of peak. The rows with visible headroom -- `o_proj` at
59.3 %, `P*V` at 49.8 %, `Q*K^T` at 57.5 % -- are together only 9.5 % of the phase, so
bringing all three to 84 % would return about 764 us, or 3.1 % of the phase. The kv-only
layer-18 row at 21.4 % of peak is a rounding error in time (0.2 %) and is listed only so the
17-full-plus-1-kv-only shape is auditable.

### Same split, proportionally worse

```
ideal time, all 660.53 GFLOP at 206.2 TFLOP/s   =  3 203.3 us
actual phase                                    =  5 933.7 us
                                             overhead 2 730.4 us
   of which  non-GEMM residue                       709.5 us   (26.0 %)
             GEMMs running below peak             2 020.9 us   (74.0 %)
```

`54.0 % = 61.3 % GEMM attainment x 88.0 % GEMM share`. The residue is twice the LM's share
(12.0 % vs 6.3 %) for a structural reason: SigLIP pays the same kind of per-layer glue -- two
norms, one activation, the attention layout copies -- over **9x less GEMM work per layer**
(24.5 GFLOP vs the LM's 221.0) and 7x less GEMM time per layer (193.5 us vs 1347.6). More
layers, each much smaller, means the fixed per-layer cost is amortized far worse.
**194 of the phase's 385 launches are residue, and they buy 12 % of the time.**

Two rows carry the SigLIP deficit:

* **`q`/`k`/`v`/`out` at 57.3 %, 31.4 % of the phase.** These are four *separate*
  [768, 1152] x [1152, 1152] GEMMs per layer. Fusing q/k/v into one N = 3456 GEMM is the
  same identity already shipped on the LM prefix (`prefix_qkv_fused.py`, which is why the
  LM's `q|k|v` row exists at all) and is not applied to the vision tower.
* **Attention at 31.1 % of peak.** head_dim 72 is not a tensor-core-friendly shape and
  S = 256 is short; 108 layout-copy launches (190.5 us) exist only to pack and unpack for it.

The patch-embedding conv runs in **tf32, not bf16** -- 206.2 TFLOP/s is not its ceiling, so
its `% of peak` cell is left `n/a` rather than printing a misleading 8.9 %. It is 1.0 % of
the phase.

## How the FLOP counts were obtained

Every `GFLOP` cell is `2 x M x N x K` over the **shapes the architecture fixes**, not a fit
and not a counter. Per invocation:

| GEMM | shape | GFLOP |
|---|---|--:|
| LM `gate`, `up`, `down` | 968 x 2048 x 16384 | 64.9614 |
| LM `q\|k\|v` fused | 968 x 2048 x 2560 | 10.1502 |
| LM `o_proj` | 968 x 2048 x 2048 | 8.1202 |
| LM `Q*K^T`, `P*V` | 8 heads x 968 x 256 x 968 | 3.8381 |
| LM `k_proj`/`v_proj` | 968 x 2048 x 256 | 1.0150 |
| SigLIP `q`/`k`/`v`/`out` | 768 x 1152 x 1152 | 2.0384 |
| SigLIP `fc1`, `fc2` | 768 x 1152 x 4304 | 7.6158 |
| SigLIP attention | 2 x (3 views x 16 heads x 256 x 256 x 72) | 0.9060 |
| SigLIP projector | 768 x 1152 x 2048 | 3.6239 |
| SigLIP patch conv | 768 x 588 x 1152 | 1.0404 |

The two phase totals that fall out -- **3756.15 GFLOP** for the LM and **660.53 GFLOP** for
SigLIP -- reproduce the independent analytic record to 0.001 % and 0.005 %. The LM's resulting
74.5 % also lands 1 point from the hardware counter `Tensor Active` = 73.5 % measured on the
same phase through a completely separate chain; that agreement is the main reason to trust
the FLOP model rather than the arithmetic alone.

Kernel-to-GEMM assignment was confirmed three ways, not inferred from names: launch count per
predict (34 = 17 layers x 2 for `gate`+`up`, 108 = 27 x 4 for SigLIP's projections), CUDA grid
dimensions against the tile in the kernel name (`down` is 32x2x**3**, i.e. split-K 3), and
launch order within a layer (`fc1` precedes the GELU whose grid is exactly
768 x 4304 / 1024 = 3228).

## What is derived, and what would make this wrong

* **The residue subtotal is derived by subtraction** (`phase total - the named GEMM rows`);
  the individual residue rows are measured. LM: enumerated rows sum to 1533.19 us against a
  subtracted 1533.17 us. SigLIP: 709.47 us against 709.50 us. Both reconcile to 0.03 us.
* **No GPU-metrics counter is used anywhere on this page.** Every time is a CUPTI kernel
  begin/end timestamp. This matters because the capture does enable
  `--gpu-metrics-devices`, whose ~50 us sampling period is longer than most kernels here
  (SigLIP's are 1.5-58 us); any per-kernel figure taken from that sampler would be
  meaningless, so none is.
* **DRAM bytes are absent by choice, not by oversight** -- see above. Every `% of peak` on
  this page is a compute-side number and says nothing about bandwidth.
* Single profile, bs = 1, no repeat sampling; run-to-run variance of the phase totals is
  unquantified. The per-kernel noise floor established for the denoise page is ~0.8 us.
* Nothing here extrapolates to batch > 1. The prefix has no batch dividend in FLOPs per
  token, but its share of the predict grows with batch because denoise does.
* `main` here is `eccaeb6`, the same build and the same profiling pass as
  [`denoise_20260803.md`](denoise_20260803.md) and the same one the README's phase chart is
  drawn from. Nothing on this page is carried across commits.
