# Denoise step, per kernel -- 2026-08-03

Where one denoise step's GPU time goes on the optimized build. **One step is 190 kernel
launches and 1239.15 us**; a predict runs ten of them.

## Measurement

| | |
|---|---|
| commit | `eccaeb6` (the tile work and the pin are in) |
| card | RTX PRO 5000 Blackwell (GB202 / sm_120), 110 SM, 96 MB L2 |
| torch | 2.7.1+cu128 |
| profiler | nsys 2026.1.2, CUDA stream 157 (the denoise stream) |
| clock | **locked 1897 MHz**, re-applied every 0.5 s, sampled throughout: 98 of 102 samples at 1897, spread 15 MHz |
| exclusivity | GPU held under `flock`, no other process |
| workload | `--stage1`, 12 predicts x 10 steps = 120 steps, bs=1, 968 prefix tokens, chunk 50, bf16 |

The clock is **locked here on purpose** -- this is a per-kernel analysis, not the headline
number. The README's end-to-end figure is measured unlocked. The two are different rulers
and are not comparable.

## Reading the roofline column

Arithmetic intensity is FLOP per byte of DRAM traffic. This card's measured ceilings are
**194.9 TFLOP/s** dense bf16 and **1222 GB/s** DRAM read, so its roofline knee is at
**159 FLOP/byte**. A kernel below the knee cannot go faster than its bytes allow; one above
it is limited by arithmetic.

At bs=1 the expert GEMMs run at `M = action_chunk = 50`, which puts their AI at roughly
`M` -- far below the knee, so the four large ones are all memory-bound and the tile work
targets bandwidth rather than occupancy. The two attention BMMs sit on the other side
because their operands are activations, not weights.

> AI is a property of the shape and does not move with the tiles. The DRAM byte counts
> behind it were measured with `ncu` on the pre-retile build, so treat the column as a
> classification rather than a current byte count.

## Reproduce

```bash
flock /tmp/pi05_gpu_timing.lock -c '
  nvidia-smi -i 0 -pm 1; nvidia-smi -i 0 -lgc 1900
  PROF_OUT=/tmp/prof CUDA_VISIBLE_DEVICES=0 bash tools/prof.sh cur stage1 12
  nvidia-smi -i 0 -rgc'
```

Then group `/tmp/prof/cur.sqlite` by kernel on `streamId = 157` and divide by 120 steps.
`tools/ksum.py` does exactly that.

WARNING: Re-apply the clock lock during the run and sample it -- the driver drops `-lgc` mid-run,
and a batch of data taken at the wrong clock looks perfectly normal.

WARNING: When bucketing by kernel name, note that inductor names a kernel after its whole fusion
chain. The post-attention norm fused into its consumer is called
`triton_per_fused__to_copy_add_gate_up_geglu_mean_mul_pow_rsqrt_*` -- it contains `geglu`,
and a keyword bucket that tests for `geglu` first will pull 18 norm kernels into the GeGLU
row. The total will still be right, which is what makes the mistake hard to see. The
`[everything else]` row above is derived as `total - the seven named rows` for that reason.
